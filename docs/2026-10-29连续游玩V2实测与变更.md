## 落地的系统修改

- 新正式链为角色本人意愿 → 主 API 事件框架 → 主 API 逐个关键场景写纯正文 → 合成一篇后事务保存。普通问答、赶路、交付等不要求玩家逐句确认；重要选择仍由玩家决定。所有叙事仍由主 API 生成。
- 场景使用同一套相对年份、年内日序、时段与可选分钟。程序只计算坐标与逐场区间，给正文明确的结束时点、日差及末态地点，不对旅行能否发生作剧情许可判定。
- 近期正文、保存的时点、角色详细表、累计因果与玩家选择一起传递；背景置前，当前场景与末态焦点置后。限知和全知显式进入正文生成。
- 多场景分别保留原回复。后场中断重用前场，不重抽整篇；真实客户端短暂断连时，后台仍完成了西幻测试 6，重新读取拿到同一篇 7159 字故事。
- 角色格式先本地恢复。完整根对象后多出的结束括号可去掉，全部字段与原文字值保留；仍需修格式时自动只修同一角色候选一次，其他已完成角色不重新生成。
- 主创框架把场景数组误写为 `scene` 时，读取层原样接入规范字段 `scenes`；已有规范字段优先，不转换单个对象，不改时间或正文，缓存原回复直接复用。
- 请求身份按实际 JSON 数据计算，忽略对象字段顺序与排版，保留数组顺序及各字段值；普通文本仍逐字参与身份。避免重启或 MySQL JSON 读回换序导致有效原稿被当成新请求。同一操作保存的原始框架也会先本地重读，通过结构及时点绑定后继续正文，不因缓存索引漂移另抽一篇。
- 用主 API 明确写出的姓名与编号对应绑定已分配身份，统一关系、物品持有人、本人经历和人物末态，不用正文关键词猜人，不把模型的另一串编号建立成另一角色。
- 人物意愿和未发表提纲不写成已发生过去；人物历史按提交记录增量归档，未知去向不默认放在玩家身边。
- 长档终章读取有来源的开篇、近章、中段重要事件和累计因果节选，原始完整记录不删除。终局承接已保存健康结果和末时点，区别确认死亡与活着主动归隐。
- 归隐尾声和死亡走马灯使用分别选择的体裁提示，末条输入以明确的 `endingContext` 重申已保存状态。归隐仍活着，只评价截至此刻的旅程；死亡才收束生命终止。兼容字段名 `death_summary` 不再被解释为每一份终章都必须写死亡。

## 保留的真实问题与修复证据

西幻测试 2 有昨日/前日指代口误；测试 3、4 有提纲末态与正文漏写或尾声日期不一致。它们没有因接口成功被称为小说完全正确。测试 5 显示单纯把 Flash 换成 Pro 也不能防止漏写南行，因此落实了按关键场景写全、逐场缓存的公共机制。测试 6 实际写完南行、交流、返程与回家，主角仍存活可继续。

测试 5 的首次连接异常保留未知用量预留；一份角色回复只多写根结束括号，加入真实夹具后本地恢复，同操作续接时未重跑已付费角色。测试 7 的本诺引用问题按同份人物关系表的明确姓名修复，恢复只增加终章调用，3919 字正文逐字复用。

中幻测试 4 已写出安顿生活，却因主创未明确交付人生状态而仍为 PLAYING；随后将普通继续、主动归隐及确认死亡的结果交接补为显式字段。测试 5 的真实候选已明确给出活着归隐，却将场景数组字段写成单数，读取失败。仅加字段兼容后的第一次恢复仍失败，多产生约 ¥0.038153 的框架调用，原失败和费用均保留；继续查出请求身份将 JSON 字符串的字段顺序算作内容变化，新增按数据计算身份和同操作原稿重读。单数场景原稿成为回归夹具，最终恢复结果见表中 EASTERN/5。

逐字阅读 EASTERN/5 时还发现：正式状态与健康值虽正确，初次终章却把正常睡下写成死亡。该实质错误未按接口成功算作通过；公共生成代码改为分别选择归隐／死亡体裁，增加明确的末条状态输入，回归同时检查两种提示互不混入。独立 QA 操作仅重新打开终章阶段进行针对性复测，旧终章原稿完整留档，不回滚或重抽 2872 字正文、不改生命值、时点或归隐结果。最终原文见本报告配套原文文件；这次终章修复不计作第 19 次新行动。

仍有少量相对日期口误、材料称呼不一致和分场衔接时的动作重复，未将其称为文学质量完全无误，也未因此取消已经完成的正文。当前优先可持续推进，细节质量随后改善。
