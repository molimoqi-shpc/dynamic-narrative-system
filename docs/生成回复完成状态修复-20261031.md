# 生成回复完成状态与多入口恢复

## 已复现的问题

本轮沿着角色截断续接继续检查开局和主创框架，共发现两个入口遗漏：

- `CreationModelExchange` 复用缓存时先解析 JSON，解析及字段检查通过就清除问题标记，因此一份供应商明确标记截断、但 JSON 碰巧闭合的候选会被直接当成完整回复。
- `ConversationOperationService` 恢复主创框架时会尝试解析操作内 `modelFailureReplies` 中的原稿。这个入口在调用统一回复缓存之前，因此仅修统一缓存仍可能被绕过。

原设计把“数据结构可读”与“这次生成已完整结束”混成同一个前提。解析器升级确实应该挽救已付费完整稿，但不能凭 JSON 闭合推翻供应商的截断或连接中断事实。

改动前已用独立随机存档、真实 MySQL、模拟模型复现 3 个失败用例：开局候选、length 截断框架、带部分原稿的 timeout 框架。三者恢复时都少了必要的同候选补全，直接采用了片段。记录：`.runtime/stability-20261031-completion-state-before.log`。

## 方案选择

| 方案 | 正确性与维护代价 |
| --- | --- |
| 一律重新生成所有非空问题缓存 | 简单，但破坏完整原稿的本地恢复，增加费用和剧情漂移 |
| 在回复 JSON 增加私有状态字段 | 可显式区分状态，但旧包会因不认识字段而无法反序列化，影响回退 |
| 增加数据库状态列 | 能明确记录，但需要迁移，并协调旧包写入行为与已有记录的状态 |
| 在已有私有问题字段加入明确状态前缀，并在恢复端分别处理 | 保持回复格式与表结构兼容；原稿和状态仍同一条 SQL 持久化；不迁移旧存档，支持回退 |

选择最后一项。新不完整记录由 `receivedIncomplete` 明确写入 `INCOMPLETE:` 状态前缀；`Saved.incomplete()` 统一识别。旧记录按当时确实写入的固定技术状态码兼容，不扫描故事文本或新增剧情关键词判定。

## 修改后的行为

1. 开局、世界观及统一结构化交换复用回复前，先读取完成状态。明确未完成的候选即使 JSON 能解析，也只补全同一候选；完整候选继续本地解析复用。
2. 统一交换仍保留已完成的原始出生正文、世界介绍和有效字段，不借补全重抽世界、人物或人生。
3. 操作内失败原稿明确记录 `incomplete`。只有内部 `finishReason=FORMAT` 表示原稿完整、读取失败，可尝试本地重解析；length、timeout 等部分回复不能从该入口直接升为完整框架。旧操作缺少新字段时，按原有 `FORMAT` 标记恢复。
4. `FORMAT` 原稿在统一交换的异常入口也按完整已接收候选保存，和操作内恢复分类一致。字段仍需正常解析，不跳过必要的保存结构读取。
5. 保留每次显式续接、每阶段原有调用限额和成功阶段缓存，没有新增自动重复请求。

生产代码涉及 `ModelReplyJournal.java`、`CreationModelExchange.java`、`ConversationOperationService.java`。没有更改前端、故事创作提示要求、六维公式、存档数据或时间地点叙事规则。
