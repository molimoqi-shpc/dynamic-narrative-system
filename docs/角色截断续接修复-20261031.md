# 角色接口截断后的保留与续接

## 问题和设计缺口

本轮检查连续游玩的角色意愿交接阶段，没有更改前端构图、角色设定、时间地点规则或主创权限。

旧流程只在角色接口成功返回时保存回复；异常分支把所有错误统一当作请求失败，跳过了异常携带的 `partialResponse`。因此模型因长度限制截断时，已经生成且已经消耗用量的角色原稿没有进入角色回复记录，故事停在主创之前，后续恢复也无法沿着该原稿继续。

原设计遗漏了两个不同的状态：收到部分回复与完全没有回复。角色缓存还把“JSON 能解析”当成了完整回复的充分条件。若只增加原稿保存却不修恢复端，碰巧完整的 JSON 片段仍可能被错误采用；另一个中断窗口是原稿已独立保存，但操作进度尚未保存。

旧实现的针对性复现共 5 个用例全部失败，见 `.runtime/stability-20261031-role-truncation-before.log`。包含不完整 JSON、能解析但供应商明确标记 length 的 JSON、同批另一角色成功、补全再次截断、补全时网络故障。

## 方案比较

| 方案 | 整体影响 |
| --- | --- |
| 全部角色重新生成 | 重付成功角色请求，可能改变已生成意愿，扩大延迟与上下文漂移 |
| 只要 JSON 能解析就继续 | 无法识别供应商明确报告未写完的候选，可能把残缺意愿交给主创 |
| 保存候选和不完整标记，只补缺失角色一次 | 保留成功回复和本人原意，控制调用次数；真实网络故障仍保留现场供显式续接 |

采用第三种，复用已有回复表和既有一次格式修复额度，不新增表或提高单次操作调用上限。

## 共用流程修补

改动生产文件仅为 `backend/src/main/java/com/bs/narrative/service/ConversationOperationService.java`。

1. 截断原稿与原因经 `ModelReplyJournal.receivedIncomplete` 一次提交，初始原稿保持不变；操作内同时保存带 `incomplete:true` 的尝试记录。
2. 从操作缓存恢复时跳过不完整尝试；从独立回复记录恢复时尊重不完整标记，即使 JSON 能解析也先补全。
3. 补全提示携带上一份原稿，要求保留本人意愿、完成同一候选，不把计划当成已发生的事实。
4. 仅供应商结构化 `finishReason=length` 且有部分原稿时，允许沿用每框架一次的自动修复。普通超时、连接、费用、限流错误不会因此自动重复请求；同批存在真实网络错误时也不会自动整批重试。
5. 成功角色及主创已完成阶段继续复用；完整独立回复恢复时优先读取其 `parsedJson`，与正常成功路径一致。
6. 不提前把尚未发表的角色意愿写入世界书。现有框架流程在故事发表时统一归档，保留该安排。

测试使用独立随机存档、实际 MySQL 和模拟模型，不调用付费供应商。新增覆盖异步交接、混合错误、重复补全的停止边界，以及原稿已保存但进度未保存时的故障恢复；恢复后还核对调用次数和完整正文发表。
