# 情境天赋：不再只有开局加点

## 原因与方案选择

原实现有三处相连的问题：生成提示只允许属性增益；`parseTalents` 无论主创生成什么描述，都会用固定的属性加点说明覆盖；`creationState` 查看未完成开局时还会再次覆盖非加点描述。后续角色附加表也没有选中天赋，因此只放宽生成提示不能让特殊作用持续参与故事。

修改前已复现两个失败：模型生成的木器听声特长在候选保存时丢失，主创框架输入中没有已选择的特长。见 `.runtime/talents-20261031-before.log`。

比较过的方案：

- 固定天赋库容易兑现，但使随机世界和人物出身只能套有限预设。
- 为每个天赋增加回血、冷却、次数、自动掉落等代码机制，会扩张状态系统，增加叙事与代码两套结果冲突，也不符合本项目由主创统一写故事的设计。
- 采用生成式情境特长：保存明确的发挥条件、作用、边界和自然代价，持续交给主创；只保留已经实现的少量开局属性作为可选附属效果。这样不增加模型调用或逐句剧情审查。

采用第三种。特殊效果通过剧情里的观察机会、办事方法、适应或交往优势实现，最终经过和结果由主创结合角色、世界和环境生成。

## 卡面内容与强度

新生成候选包含 `special_effect`：

| 字段 | 含义 |
| --- | --- |
| trigger | 何种场景、需要哪些实际条件 |
| benefit | 一项区别于加点的具体特长 |
| limits | 做不到什么、受哪些自身能力或环境约束 |
| tradeoff | 自然代价或干扰；没有则留空，不强加惩罚 |

模型根据已固定世界与玩家三问生成至少三个不同候选，最终选一个；不是新增一套固定天赋池。描述建议合计约 80—150 字，存入既有 TEXT 字段时整理成可读卡面，不把 JSON 直接显示给玩家。

例如木匠可在近距离轻敲熟悉木器时较易察觉空腔或松动，但不能隔墙得知内部，更不能直接知道机关用途，嘈杂会干扰判断。它带来调查方法和发现机会，不直接给出谜底，也不是必然成功。

新候选允许 `stat_key` 为空，即完全不加属性。若附带相关基础属性，只给 1—2 点；旧版已保存的加点候选仍按原卡面生效，原有 2—6 点不被削弱或重复发放。所有档位都只是一项有限特长，不能默认神性、无敌、全知、无限资源或保证他人服从；现代普通世界不因天赋获得魔法，超自然世界也依其既有边界设计小能力。

## 持续游玩数据流

1. 统一天赋协议新增可选结构，兼容旧版已付费候选，不因升级重抽。
2. 开局解析保留主创的特殊作用及条件，出生提示按已选卡面塑造人物，不凭天赋名称擅改身世。
3. 查看开局草稿不再修改已保存描述；重复提交相同回答、重复选择或刷新仍复用原结果。
4. 每段组装本人上下文时，按当前存档与角色查询已选天赋，放入附加表 `identity.talents`。未选候选、其他存档与未公开的玩家特长不会流入别人的角色接口。
5. 主创框架和正文都携带该附加表。统一说明要求相关场景实际考虑特长，不只提名称，也不在无关场景机械触发；已有开局数值不重复加点，特殊作用不另掷检定、不凭文案直接修改生命、六维、过去事实或世界规则。
6. 天赋在开局选定后保持不变，沿用已有存档记录；回溯故事不重抽天赋。旧版无实现依据的自由描述仍标为旧版记录，不自动激活其夸张承诺。

人物面板不再把新情境天赋标成“未实现的旧版天赋”。天眼资料使用中文标签展示作用类型，同时隐藏仅供主创使用的执行说明。没有更改主界面构图、导航或输入区尺寸。
