# 系统检查、分支缓存修复与必要功能

## 本轮范围和结论

按登录、世界生成、三问天赋、出生、连续生成、角色与物品、记忆与世诰、异常续接、读档回溯、终局、费用记录和备份逐项检查。用户后续明确要求优先于早期文档中的固定神明、微动作判定和目标通关等旧描述。

本轮修复一个已复现的共用缓存归属缺口，并完成全量离线回归。已有主流程有实现和测试依据；玩家级安全备份恢复、独立测试数据库、主生成通道就绪诊断、累计预算管理仍是必要补足项。不能把流程回归数量当作长期小说质量的保证。

## 已修复：回溯后新行动误用旧分支原稿

操作表的正式身份是 `session_id + branch_epoch + operation_id`，但主创框架和正文的回复缓存只根据所传输入求哈希，输入没有显式分支身份。原设计隐含假设操作 ID 永远不会重用，和实际接口允许各分支分别使用该 ID 的约定不一致。

旧实现已复现：完成一次行动，回溯到初始状态，再在新分支用同一操作 ID 和相同行动提交，角色接口重新执行，但主创框架只执行了一次。新行动直接复用了被舍弃分支的原稿。记录：`.runtime/system-audit-20261031-branch-before.log`。

比较方案：

| 方案 | 影响 |
| --- | --- |
| 禁止不同分支重用操作 ID | 增加客户端限制，没有直接补齐缓存的正式身份 |
| 回溯时清空回复缓存 | 丢失已付费原稿，破坏半途恢复；迟到请求还可能重新写入旧缓存 |
| 新行动携带正式生成身份，恢复同一未完成候选时保留该身份 | 分开新行动与旧候选，保持重复提交幂等，并复用检查点内同一候选的已完成阶段 |

采用第三种：新行动创建 `replyIdentity`，使用既有分支号和操作号；每个框架附带自身 frame。框架和正文同时携带该身份参与已有缓存键。检查点保存并恢复同一个未完成候选时保留原身份；旧版正在进行的操作未带该字段，继续沿用原缓存键，不因升级重付费用。

生产修改仅涉及 `ConversationOperationService.java` 与 `SceneStoryService.java`。没有新增数据库表、剧情时间地点门禁、模型调用或前端布局变化。

新增 4 个测试用例：三个独立随机存档分别验证跨分支重用操作 ID 时框架和正文均独立生成，同分支重复提交不再次调用；另一个验证回溯至未完成多场景故事的检查点后，已写完的前场景不重写，角色与框架也不重算。

## 实际数据与接口检查

筛选口径为排除密码标记为 `unused` 的临时夹具账号，包含演示账号和既有独立 QA 账号，共 48 个存档。关联检查中，存档所有者缺失、可游玩存档角色缺失、场景缺失、活跃存档归属不符、待处理操作指针悬空、当前玩家角色或场景不一致均为 0。没有据此推断正文内容一定正确。记录：`.runtime/system-audit-20261031-data-links.json`。

通过正式前端代理登录演示账号，人物面板、目标、存档点、结局、世诰、剧情卡、视角和章节接口都可读取。车站档仍为 `ONGOING`；入梦下私有天眼接口为不可用。记录：`.runtime/system-audit-20261031-gameplay-reads.json`。

对车站旧展示档三轮的首、中、尾文本作衔接抽读：线索从广播名单、断开的线路推进到旧车票记录和北方第七站，有可承接的调查方向；同时发现以下文字质量问题：

- 第二轮中“那张票现在在哪？”和“在我手上。”均归给沈砚，说话者归属有歧义。
- 第三轮先说“三个人来的”，后又说“那四个人里”，人数指代不一致。

这属于生成文本质量，不能用格式通过掩盖，也不能凭词法规则中止故事。旧的已发表正文没有被改写。本轮没有新付费生成，不能据旧样本抽读声称新提示已解决这些问题。后续真实验收应覆盖独立新档的普通推进、跨日、物品交接、重大决策和终局，并人工阅读人物对白与因果，不只检查时间和接口状态。
