# 游戏功能联查与修复（2026-10-21）

本轮检查范围包括人物创建与姓名、直接交流与普通行动、打听与见闻、移动与场景落点、交手和身体状态、重要物品、人际与盟约、世界书限知展示、目标与结局、存档回溯。保留主API依据各人意愿创作故事的路线，没有新增用剧情关键词决定能否行动的规则。

## 修复的问题

1. 新获得物品的服务器编号只在提交时生成，同一主API响应按名称回写资料时却找不到物品。现在支持唯一的真实持有物名称引用；同名多件或失效编号不猜测绑定，不凭面板资料授予物品。
2. playerJournal中的姓名可能覆盖已经确定的真实主角姓名。现在附加资料只补全占位姓名，保留玩家原始自述和既有身份。
3. 实际接口检查发现林野旧档使用“我是普通旅人林野”，旧兼容逻辑只识别“名叫”等形式，仍显示未留名。现在以出生故事开头的主语与玩家本人自述相互印证后读取；不从NPC名字或老师、父亲的介绍推定主角名字。面板读取仍不改写存档。
4. 较新的OBSERVED_STATE记录会将“双方实际同意结盟”等依据覆盖成“曾经见过”。现在保留具体关系依据，同时更新所见时间。
5. 夺取物品放下再拾起后，最后一条记录变成PICKUP，原实现将它误标为借用。现在从实际交接历史保留夺取性质，明确归还或赠予后的状态相应更新。
6. 见闻面板使用排除列表，新增内部摘要类型可能混入见闻并挤走线索，内部物品资料也可能经旧分享入口转发。现在展示和分享都使用已支持的见闻来源集合，内部存档仍供相应上下文读取。
7. 分享、求证草稿原来只有标题，较早的消息可能不在最近上下文中。现在同时携带玩家选中的原记录、来源及已有核对结论；超长正文明确标为节选，保留在输入长度内。草稿不自动发送。
8. 盟约回应按钮残留必须同场的前端限制。现在不在最近所见的人也能拟定“尝试联系”的行动草稿，联系是否成功、对方如何回应交给主API。附近明确对象仍使用直接交流草稿。
9. 未选中交流对象时，打听地点会被卡在“必须选在场者”。现在先拟定寻找可接触知情者的大致行动，由正常故事链处理，不直接返回凭空获得的消息。

## 组合测试与实际接口

新增完整链路测试使用模型替身与真实MySQL：第一回合取得剧情信物、记录同行关系与生命；第二回合赠出信物、疗伤并分道；回溯第一回合后，重要物品、关系与生命一起恢复。测试独立会话结束后按会话编号清理，没有重放用户真实故事。

后端204项、前端64项检查通过，后端打包及前端生产构建成功。覆盖角色创建、故事模式、交手处置、物品归属与消耗、身体状态、见闻、世界书、目标依赖、存档回溯，以及前端分支恢复和草稿。

运行中的新包对2个已有存档分别检查9类接口：场景、人物面板、目标、正文历史、世界书检索、访问地点、记忆、结局、回溯点。林野的长期存档仍为PLAYING，生命100，结局ONGOING；旧档姓名现在准确显示林野。独立测试存档仍正常显示月魄镜和师徒关系。限知角色卡无私密附加表。

读取前后逐表摘要相同，包括人物、物品/知识、章节、世界书、目标、运行状态、回溯点和调用账单。运行服务已恢复正常24次操作额度，后端健康UP，前端5173可用。
