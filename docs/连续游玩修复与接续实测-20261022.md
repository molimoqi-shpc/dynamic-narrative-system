# 连续游玩修复与接续实测（2026-10-22）

## 本轮修改

- 只从实际发表过的章节中取最近四章及开篇，失败或取消的空日志仍保留，但不会挤掉故事前文。
- 剧情补充记录、长章节和天眼角色记录先筛出小字段，再排序取回完整资料。处理了真实复现的 MySQL 1038 排序内存不足；包含 1 MB 存档和低排序缓冲区测试，不以提高数据库内存掩盖问题。
- 页面首次进入及重新读取时，场景与正文按同版本成组应用；后台恰在两次读取间保存时，最多重新读取三次。只读同步不提交新行动、不追加模型调用。
- 异步生成提交、查询、恢复，以及场景和正文读取使用 20 秒请求超时，超时后保留原操作编号。服务端继续完成时可查询取回，不重新发送同一行动。
- 修正服务器恢复不同视角时页面可能不释放加载状态的问题。
- 修正历史正文接口遗漏重大选择 stakes 的问题；完整保留已公开后果，继续屏蔽主创私有构思。历史选择标为“当时的选择”，不会冒充当前待回答的问题。
- 实测发现：正文与人物末态表已明确主角离开账房，重复的场景结果表却为空，导致界面仍显示账房。现在直接保存主 API 的明确末态落点，兼容旧场景组；不读取剧情关键词、不判断是否能抵达、不替主 API 改写经过。
- 归档中的可选“无变化”数组及空对象兼容缺省/null，不因无交手却漏写空交手表而打断故事。归档原回复在格式处理之前持久保存；恢复可复用已经能读取的回复，不能读取时仅补归档。缓存签名按对象键排序后计算，数据库重排 JSON 键不会误认为新稿；专门模拟旧序列化失败后的恢复，检查没有新增模型请求。
- 主创交付格式将 story 正文置于可选内部构思之前，修复本轮实际出现的连续“只返回构思、没有正文”。较长的实际正文和承接摘要不再因任意 18000/6000 字符阈值被拒绝。
- 角色意愿请求只围绕主创选定的当前参与者、明确角色查询及当前行动，旧剧情引用和旧关系记录不再被递归误当作当前出场人物。已知角色的历史引用不因缺少本段私有档案而变成“身份缺失”。旧版因此丢开但已经归档的定稿可按稳定签名恢复，跳过无关角色调用，不重写正文。

## 程序检查

相关后端测试 **490 项**、前端 **101 项**（86 项组件测试、15 项 Node 工具测试）通过，前后端打包成功。后端统计按测试方法去重，不叠加重复运行。覆盖失败/取消后续写、保存恢复、回溯、长存档查询、限知与天眼、公开选择后果及末态表落库。

首次批次中复现了大 JSON 排序故障；低缓冲区测试进一步证明，仅改变 SELECT 字段仍不足以隔离 MySQL 排序，需要将小字段中间结果明确物化。修正后回归通过。测试夹具中的版本参数及天眼开关也已修正，不把夹具错误算成产品缺陷。

## 真实接续：保留一次失败，原场景修正后复测

沿用昨天的独立 QA 存档。八段简短早期文本是测试夹具；昨天实际生成的核账与担保提议作为前文。本轮共三个行动操作尝试，其中一个为撤回的失败出行分支；最终分支连续保留两次新行动。续写中的构思回复、格式失败和恢复费用均计入，没有推进或修改用户的原长期存档。

1. **拒绝新担保。** 主角明确拒绝，陆绫接受这一答复并结束谈话；旧账与新担保分开，没有反复再问同一选择。实际一次成稿 685 字符，角色、主创、归档各一次。
2. **首次独自出行未通过。** 正文已描写西闸查看与回程，末态表亦写回程途中，但 sceneOutcomes 为空，保存后仍在账房、陆绫仍显示在场。失败的 1492 字符正文、原始结果和费用全部保留，不能因状态为 COMPLETED 就算连续游玩通过。
3. **同一出行段复测。** 通过正常回溯接口回到拒绝担保后的检查点，重新提交同一行动方向。期间实际遇到归档缺省空交手表造成暂停；修正后恢复同一操作，先将 958 字符定稿原样归档发布，主角位置正确保存到西闸，陆绫留在账房。主创原先返回 CONTINUE，接下来两次却只输出构思，均保留为未发布候选；修正交付格式后，已生成续写和归档，又暴露了历史人物被误当当前参与者、从而清掉定稿并重复取角色意愿的问题。修正这一数据范围后，最后一次恢复直接复用已付费的 1406 字符续写及归档，没有新增模型调用；已发表首段逐字保留。完整结果以原文和机器证据为准，没有手工补写剧情结果。

人工阅读的范围是这组核账、拒绝、独自实地查看的相邻片段。第一段人物回应有依据；出行段能完成所求查看并留出下一行动，场景归档缺陷被实际发现。观察与说明仍占较多篇幅，不能据此认定稳定达到成熟小说的长篇节奏。完整原文含失败分支，不润色、不隐去失败。
