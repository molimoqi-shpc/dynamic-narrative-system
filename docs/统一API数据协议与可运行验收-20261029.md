## 当前正式生成链（AUTHOR_RESULT_V2）

新操作统一使用：本人角色意愿 → 同一主 API 的 STORY_FRAME → 程序绑定时间坐标与地点目录 → 同一主 API 的 STORY_TEXT 纯正文 → 一次事务保存正文与实际结果。角色 API 不创作最终故事；程序不裁定旅行是否允许、同伴能否到达或剧情是否成功。

STORY_FRAME 只返回少量实际场景、起止时点和重要结果，不塞长篇正文。STORY_TEXT 直接返回纯文本，不再让几千字小说同时承担 JSON 转义，也不另调模型估时、审稿和重新归档。多场景时，同一主 API 依次写完这些关键场景，每场接收同篇已完成前段，全部写完后拼成一篇并一起保存，避免把全部篇幅用在第一个小事件、漏掉后续南行或返程。玩家不需要逐场确认。每场原回复独立保留，后场中断只续缺失场景。

正文同时接收近期已发表原文及其保存的起止时点、累计因果、原始身世、详细角色表、玩家方向和重大选择上下文。背景在前，当前未发表框架与本场写作焦点在后；末场直接给出最终时点、主角末态地点。限知与全知显式传递。

时间使用故事相对年份、年内日序与时段；精确分钟可选。新篇起点从已保存当前时点读取，不能被另一份起点覆盖。主 API 给出同一框架内的末尾与场景时点，程序只做一次坐标换算。时段对应秒数为兼容显示估值，不宣称真实精确耗时；回忆、设想和并行场景不会重复推进当前时间。旧档没有结构化时点时由主 API 明确恢复起点，不默默填午夜或零秒。

已付费框架、角色回复和正文分别保留原稿。未发表候选的角色心理、打算与资料不写成正式过去；正文截断时恢复同一框架，不重跑角色或重抽情节。保存、读档和回档仍有事务与分支隔离；这些保护不参与创作剧情。

按用户最新要求，轻微措辞、日期指代或描写偏差不触发取消与重写。角色结构错误先进行不改内容的本地格式恢复；仍需模型处理时，同一操作自动只修这份角色候选一次，已完成角色回复不重抽。名字与编号的显式对应可把模型的另一串引用绑定回已分配的角色，不用正文关键词猜人，不重新创建角色；有冲突的姓名不会被强行合并。

死亡终章接收同次已保存的末时点与健康结果，明确把末场收束到已确认死亡，再写走马灯；活着的主动归隐保持 RETIRED，不因目标完成或普通休息结束世界。

重要证词、交接或邀请中的具名普通人物使用 EXTRA 简表；背景人群可以概述。未知末态不会默认放进玩家场景。角色本人历史按已提交记录增量导入，避免每轮重新复制同一历史。

长档终章使用原始开篇、最近章节、重要中段事件与累计连续性节选；明确标注节选来源，不删原文，不因资料缺失断言没有婚姻、子嗣或某段人生。原始完整记录仍可在存档中读取。

旧操作按自己已经保存的版本恢复。下表 AUTHOR/REVIEW/ARCHIVE 等阶段继续用于旧版本兼容，不是新游戏每轮都调用的链路。

## 单一格式定义

`backend/src/main/java/com/bs/narrative/llm/ModelProtocol.java` 是格式定义源。由它生成实际请求里的阶段schema，同时用于读取已返回字段的类型。正式请求展示一种规范格式，旧字段保留在兼容读取器中，不再作为另一套可选格式同时给模型。

|阶段|模型输出与职责|
|---|---|
|WORLD|世界标题、时代、文化、介绍、摘要、边界及三问；按存档固定|
|TALENTS|性格标签与至少三个不同名称的真实候选，不以固定天赋补位|
|BIRTH|唯一主角姓名、出生正文、初始现场、本人开局经历、物品与已知关系|
|OPENING_ITEMS|只修当前出生稿的物品登记，不重写人物和故事|
|OBJECTIVES|从实际玩家所求整理阶段目标；完成不等于世界结束|
|ROLE|根层五项意愿、分级及角色表；CORE十二分区，EXTRA简版；不生成最终故事结果|
|STORY_FRAME|新正式链：同一主 API 确定实际事件、场景时点、末态与重要结果，补资料时请求本人意愿|
|STORY_TEXT|新正式链：按同一框架、前文及人物表输出完整纯正文；文本传输，不附 JSON 对象规范|
|DIRECT_AUTHOR|早期一次回复同时交正文与结果的操作版本，保留恢复兼容|
|AUTHOR|完整正文、实际耗时、停点；需要补资料时使用明确的请求字段；主API创作实际结果|
|REVIEW|逐段修订、参与人物、是否改过时序；原耗时有明确错误时才显式纠正|
|ARCHIVE|唯一已定稿的结果记录：地点目录、人物末态、本人经历、重要物品、关系、剧情与公开卡；不再重写正文或另估时间|
|ARCHIVE_EDIT|仅兼容旧的未定稿归档流程，保留其编辑交付；不混入正式只读归档说明|
|ACCOUNTS|同一主API整理重要剧情账目及来源，不进行日常钱袋模拟|
|TIME|只读已有正文的时间记录|
|PUBLICATION|旧专门定稿交付，和只读时间记录区分|
|ENDING|已实际死亡或已实现的主动归隐之后，生成此生终章与终评|
|GENERAL|旧冻结路径共用JSON传输规范，保留原阶段字段兼容|

实际使用的阶段schema可由代码导出，不手工维护一份相互漂移的平行定义。版本标记为MODEL_PROTOCOL_V1。它规定数据结构，不替角色决定行为、不用关键词判断剧情是否允许发生。

## 统一解析和保存

- 底层JSON模式和业务读取共用严格JSON读取逻辑。不能将两个对象中的后一个悄悄丢掉，也不能默默用重复字段的最后一个值覆盖前者。
- 兼容旧围栏、全角分隔符、明确可修的引号/尾逗号等传输问题；解码后的原文不因此改写。真正截断、错类型和缺少必要资料保留原回复，由对应阶段恢复。
- 新正式链只保存同一 STORY_FRAME 的坐标换算结果，STORY_TEXT 不另估时间。旧主创、定稿、归档操作继续使用其已冻结的时间协议。
- 角色意愿、作者候选与已经发表的结果分开。仅有意愿不自动改位置、归属或关系，未发表候选不当成下一篇历史。
- 可选立绘资料继续容错，不因缺图或外貌附表错误阻止故事。
- STORY_FRAME 的完整场景数组若误写为单数 `scene`，读取层原样映射为 `scenes`，复用已付费候选；已有 `scenes` 不被覆盖，不将单对象猜成数组，不改正文、人物或时点。真实失败原稿已作为回归夹具。

## 创建阶段的已付费原稿

新增`model_reply_journal`，独立事务保存世界观、天赋、出生及物品修复的原回复。创建事务失败回滚时，原回复仍在。

身份由存档、阶段与真实创建输入共同确定。单纯升级协议说明或解析器不触发重抽。合法回复直接复用；格式异常的下一次明确重试只修同一候选。已完整生成的出生正文等根层文字保留，格式修复不能借机改写人生。一次尝试不会在格式错误后静默重抽一整篇。

输入消息中的合法 JSON 对象或数组按数据内容参与身份计算，不将对象字段换序、缩进变化当成新输入；数组顺序、字段值及普通文字保持原义，真正不同的输入不混用。旧的精确身份仍可读取。同操作保存的失败原回复在可本地恢复时先重读框架，不因数据库 JSON 换序再请求主创。

删除正常创建中的固定备用天赋补齐逻辑，以及未使用的固定神明出生备用文案。候选不足三个时返回可恢复错误，后续补足来自主API，而不是服务器编造选项。开局物品修复的具体字段检查也进入同一缓存恢复链，避免缓存一份虽然语法合法、但仍缺登记行的回复后永远无法恢复。

## 人物末态的规范交接

同一次归档以`endingPlaces`定义每个粗粒度地点，`endingCast[].placeKey`引用该目录。主API给出谁实际在哪里；程序统一复用或分配地点编号。新格式中随手附带的旧sceneId不覆盖已明确的placeKey。

这一调整对应真实故障：盐栈管事的文字末态正确写在盐栈，四个人却被填入同一个驿舍编号。原失败回复和本地替身复测分别保留，没有手改原稿制造通过。
