# 故事恢复机制的工程修补记录

## 用户要求与本轮重点

用户要求以整个系统的完整性、稳定性、可持续游玩能力为目标；修改前追清问题和原始设计的缺口，比较可行方案的整体收益与代价，修复共用机制，并检查相邻流程。该要求已记录在项目根目录 `AGENTS.md`，供后续维护遵守。

本轮优先处理故事生成与恢复的数据一致性，没有增加新界面或剧情判定。上轮尚未生效的主创格式自动修复也已启用；当前运行版本同时包含两轮修补。

## 根因：原稿与“不完整”标记分开提交

`ModelReplyJournal.received` 原先先保存收到的原稿，并把 `issue` 置空。对于截断回复，调用方随后再用独立事务写入 `issue`，表示正文尚未完成。

问题发生在两次提交之间：第一笔已经成功，第二笔因异常或进程中断未能完成，数据库中就出现“正文只有半截，但未完成标记为空”的记录。正文恢复路径将标记为空且非空的文本视为可复用完整稿，从而直接发表半截正文，场景却可能按完整框架推进。

原设计考虑了保存已付费原稿和恢复时复用，但遗漏了两个前提：

1. 收到原稿不等于已经完成，两个状态不能在保存窗口内混用。
2. 恢复端依赖的完成标记必须和原稿一起持久化，不能由另一笔独立提交补写。

故障注入测试在旧实现上实际得到：预期完整章节“……下午返回工作间……”，实际发表的却是“**两人刚走出门，主角还没来得及**”。复现日志：`../.runtime/stability-20261031-atomic-reply-before.log`。

## 方案比较与选择

| 方案 | 收益 | 代价与缺陷 |
| --- | --- | --- |
| 恢复时总是重写正文 | 绕开错误缓存 | 重复支付成功阶段，可能改写已完成场景，损害连续性 |
| 根据长度、句号等猜测完整性 | 实现简单 | 不能可靠区分短而完整的场景与截断文本，容易误判正常故事 |
| 原稿与已有完成标记一次提交 | 消除这类中断窗口，保留付费原稿并正确恢复 | 需同步调整所有已知不完整回复的写入路径；沿用现有表，无需迁移 |

选择第三种。它直接消除已复现故障的原因，不改变正文或模型输入，不增加请求，不引入新的数据库状态列；失败路径还减少了一次独立写入。

## 修改范围和相邻流程

- `backend/src/main/java/com/bs/narrative/service/ModelReplyJournal.java`：新增 `receivedIncomplete`，在同一条 INSERT/UPDATE 中保存原稿和不完整原因。完整回复仍使用原入口；初始原稿保留不变，修补结果写入最新回复。
- `backend/src/main/java/com/bs/narrative/service/SceneStoryService.java`：截断、空正文的保存采用新入口；完整正文经过空值检查后按完整回复保存。
- `backend/src/main/java/com/bs/narrative/service/CreationModelExchange.java`：开局和结构化交接的截断原稿也采用同一原子写入入口，避免维护两套失败保存规则。
- 结构化回复复用前原本就会重新解析，其行为保留；本次未给故事内容新增时间、地点、物品或措辞审查。

故障恢复测试使用独立随机存档、实际 MySQL、模拟模型，并在旧的第二次标记写入处注入故障。新实现恢复后发表完整正文，保留原始截断原稿，正文调用恰为一次截断加一次补全；框架与角色请求各只执行一次。
