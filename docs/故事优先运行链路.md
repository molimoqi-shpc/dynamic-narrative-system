# 故事优先运行链路（2026-10-20）

正常新回合默认启用 `game.story-first=true`。这是 API 创作互动故事：角色 API 提供各自的即时档案、过去理解与下一段意愿，主 API 收到这些资料、玩家行动、前文与世界书后，统一创作全部正文、对白、意外、进展与结果。程序保存结果，不以小动作模拟决定故事。

## 一段故事如何完成

1. 冻结本次角色各自的资料，分别调用角色 API。重要人物继续使用详细模板；普通龙套只填简版。角色可在 `itemIntentions` 中表达相关物品的使用、交接对象与条件，没有相关内容则为空。
2. 主 API 读取双方意愿、玩家方向、最近完整正文、累计故事记忆和各人的独立档案；需要较早详情时按世界书索引查阅。
3. 主 API 写完整事情的发展与结果。问询、关怀、调查与赶路自然衔接，普通对白不要求逐句登记。`events=[]` 是有效结果。
4. 主 API 同时返回实际有新亲历或重要处境变化的角色的 `roleExperiences.experience` 与累计重要处境 `situation`。心理、未公开往事和所见所闻按各人区分；玩家正文不替代所有 NPC 的个人记忆。出发人物名单不是必须逐人填表的清单，省略者保留旧记忆。
5. 程序在短事务内保存正文、各人的经历与必要的重要结果。下一段角色 API 读取自己的新经历、累计处境和此前心理。模型请求在事务外；失败不把半段结果当成已发生，恢复优先复用已有角色回答。
6. 普通事情到实质结果结束；需要新现场人物意愿时内部 `CONTINUE`；只有真正需要玩家决定的结盟、敌对、表白、重大承诺或风险等才 `DECISION`，停在玩家表态之前。

## 抵达与意外由谁决定

完全由主 API 根据人物意愿、玩家行动和前后文创作。同行意愿不保证抵达，也不会让程序自动移动所有人。主 API 可以写出分别抵达、改变主意、遇阻、落木、失散、留在半途或救援等具体发展。

`MOVE` 只是主 API 已写出的实际场景变化。`NEW_DESTINATION` 只是本段新地点编号的引用方式，不是同行判定。没有实际抵达的人不提交抵达结果。程序不会用旧路线门槛、物品许可、本人清醒或束缚状态否定主 API 已写出的移动；例如昏迷者被抬走仍可正常保存。

主 API 也能写 NPC 独自探路而玩家留在原地。该 NPC 的新亲历保存到本人档案，未见闻者不会因此自动知道探路发现。地图索引不负责决定可发生的剧情。

## 只保存会影响后文的结果

- 正文与各人的真实经历、重要关系、承诺、线索和处境。
- 实际持有人或物品留在哪个场景；借还保留同一物品编号。意愿本身不转移物品。实际取得有用物品用 `GAIN`，用尽或损毁用 `USE_UP`；不靠固定动词、材料白名单或逐字证明决定是否发生。
- 重要场景事实用 `FACT`；重要清醒、束缚变化用 `BODY`；实际伤情或治疗结果用 `HEALTH`；场景变化用 `MOVE/EXPLORE`。
- 不登记手中、篓边、脚边、换手、站姿、衣角、转头或每片草。旧模型回显的纯微动作状态不再进入正常保存链路。

正常故事提交使用独立的结果保存分支，绕开旧微动作执行器。新流程不再用固定台词解析另建盟约、承诺状态来决定人物关系；关系与约定由主 API 的真实故事和人物累计处境承接。

保留 JSON 结构、引用属于当前存档、数值范围、重试幂等与整段事务等数据完整性检查。它们不替角色选择，也不通过关键词评价正文的剧情含义。

## 兼容与回溯

不新增细碎模拟表，不清库，不手补真实故事状态。原有世界书、人物记忆、物品记录与检查点继续使用。旧协议操作按冻结的版本恢复；新操作的故事优先标志随操作保存，避免恢复时被配置切换改变协议。各人的累计处境是私有状态，不作为可直接转发的公开消息。

验证证据和真实模型用量见本次聊天的 `outputs/故事主创权与连续游玩验证.md`。模拟模型测试验证保存行为，真实正文仍需逐段审读，不能用测试数量代替故事质量。


## 真实输出兼容与新龙套承接

重要结果可以直接列在结果数组里，不强制逐项提供微动作时间或 ACTION 外壳；缺省时间只作存档顺序标记。新地点资料创建不自动移动人物，只有主 API 明确写出的抵达才更新所在场景。既有同行者不会因出现在新场景人物列表中被克隆。

主 API 用 `newCharacters` 提议新人物的稳定称呼及简版设定。服务器只暂存人物提案，取得此人自己的角色 API 意愿后，再让主 API 完整创作最终正文。新人物实体、本人经历和最终结果在同一次短事务提交。最终放弃的候选不留下幽灵人物或记忆。

`castPlanning` 只传候选人物设定和编号；未提交的候选正文、对白与移动不传作历史，不能从候选末尾继续而漏掉整段赶路和前面的问答。发现更多新角色时累积候选设定，复用已经取得的其他角色意愿。旧版本未提交候选在恢复时由运行流程迁移，重新创作完整正文，不手改真实存档。

最终结果明确用角色编号引用某个候选人物（个人经历、场景分组或重要结果），即选中该候选；即使漏了重复介绍，也可复用暂存身份与最终本人经历落档，不另付费重写。没有被最终引用、也未放在最终人物列表的候选仍可放弃。这里仅读取结构化编号，不从故事关键词猜出场者。

`sceneOutcomes` 协议下，人物资料不另带 `sceneId`，旧模型回显的该字段不再作为第二个场景来源。新人物默认在玩家本段结束地点；若实际在别处，由主 API 将其候选编号放进明确的场景结果分组。已明确分组者以实际分组为准。

## 正常链路的整体边界

新故事使用 `AuthoredStoryBinder` 和独立的重要结果保存分支，旧校验仅供冻结的旧协议兼容。正常链路已撤掉逐事件时间、六小时上限、到达后的对白边界、出发名单资格、清醒/束缚资格、路线物品/目标许可、新地点网格与四人上限、对白逐字证明、制作采集关键词及材料清单、选择必须绑定最后一句 NPC 台词等剧情判定。重试提示也使用独立故事协议，不能重新注入旧限制。

整段 `elapsedSeconds` 只推进故事时钟。`sceneOutcomes` 只保存主 API 写出的实际场景变化，未移动者无需填表，空数组有效；已有地点复用 `locationIndex` 的编号。外出人物返回玩家当前地点仍会保存会合结果，不拿玩家当前位置代替每个人的位置。离开前留物等结果可以附原 `sceneId`。

保留的检查是存档数据一致性：JSON 和字段容量、ID 属于本存档、同一人不能在同份最终结果里有两个落点、数值可保存、幂等和事务。它们不能按关键词解释故事，不能替主 API 决定是否抵达或人物是否愿意。主 API 未声明的交接或移动不由程序从正文猜测补造。

新人物尚未确立六维时，交手机制查询返回 `NARRATIVE`，由主 API 据其档案及意愿创作实际结果，用 `HEALTH` 等保存，不用数据库中性占位数值替人物判胜负。

## 连续章节中的既有人物上下文

角色上下文准备不再因为昏迷而跳过本人档案；其个人记忆仍不能包含失去意识期间的见闻。正常场景人物、明确交谈对象和最近两章正式引入的人物提供本人意愿，后者用于防止旧版本落点记录遗漏使刚出场人物失去上下文。只读取已提交的结构化人物介绍，不从正文关键词猜人，不提前搬动人物。

`characterIndex` 提供本存档真实人物的编号和姓名。需要其他既有人物的新意愿时，主 API 返回 `roleRequests:[{roleId:真实编号}]`；服务器读取该人自己的身体、物品、私有经历、累计处境和心理，再调用其本人角色 API，将结果交回主 API 完整创作本段。重复请求复用本段已有回答，失败续接也保留已经取得的回答。新人物仍使用原来的暂存提案流程。

`currentState.recordedSceneId/recordedLocation` 说明该人档案当时保存的地点，便于主创对照前文，不是是否能登场或移动的许可。档案和意愿按该人自己的记录地点归档，不错误记成玩家当前地点。读取别处人物不自动移动他、不替他创造新经历，也不让他读到玩家的全文或其他人的秘密。实际故事和落点仍由主 API 返回并一并保存。

最近人物查询先对操作编号排序，再按主键读取完整记录，避免 MySQL 对数百 KB 的冻结上下文整体排序而耗尽默认排序内存。开发回归包含 1 MB 旧操作记录，运行时不调整全局数据库参数，也不截断历史故事。

## 回访人物与页面续接（2026-10-20 后续修复）

主 API 的结构化参与人物引用（个人亲历、场景分组、重要事件及交手参与人、选择对方）可以直接触发缺少的本人角色 API，不依赖模型额外填写 `roleRequests`。已建立人物不重造，已有回答不重抽。补齐期间没有故事结果提交，主 API 收齐本人档案与意愿后重新完整创作本段；它可以按人物意愿改变候选发展。程序不从正文或地点关键词抽人，不决定见面、移动、结盟或意外。

旧介绍序列化曾把新人物的出发地点回显误写成最终地点。正常新行动开始时，一次性按当前仍然发布的完整章节及其 `sceneOutcomes` 协议补正这类记录：未明确分配其他落点的新人物使用本段结束地点，后续已经提交的移动优先。只处理确实由该章创建、仍留在旧错误地点的介绍记录，不重放其他分支的未发布内容。修复来源单独以私有 `STORAGE_REPAIR` 记录留档，不增加剧情、时间、物品或模型调用；与正常操作一起保存检查点，回溯恢复旧资料时也恢复修复标记。历史重复地图节点没有在此流程中删除。

前端在响应丢失、结果未知时自动查询同一个操作编号，不重复发送行动；暂时断网时逐步延长查询间隔。已确认接受的原输入清空，玩家新编辑的下一步保留；服务器确认没有登记时恢复原输入。等待计时沿用同一操作的开始时刻，不因每次查询清零。`PARTIAL` 暂停需要玩家主动续接，尤其调用额度用完时不会自动追加付费请求。

## 换地点后的重要事实承接

主 API 另收到 `establishedStoryFacts`：玩家此前在不同地点已经得到的重要发现，直接复用既有 `SCENE_STATE` 记录，不重复生成、不增建逐物件模拟表。按地点与事实主题保留最新结果，附原地点和记录顺序；只传简洁的主题与事实正文，不反复携带旧过程大模板。模型累计摘要即使漏写，也不会删除这些原始发现。

这是主创上下文，不进入 NPC 本人的角色 API 输入，不让未亲历者凭空知道秘密；注明为某人说法的内容仍保留其来源，未知收件人不等于已见寄包重新失踪。主 API 自主处理不同人的认识、记错、反口或隐瞒，程序不以文本关键词判断剧情或拦截提交。旧记录格式异常会跳过此附加索引，不让无关旧资料阻断新段落。

## 已发布段落与未发布候选的写作范围

`generationScope` 在每次实际主 API 请求前根据 `alreadyHappenedThisChapter` 刷新，兼容暂停前冻结的旧上下文。`NEW_PASSAGE` 表示本轮尚无已发布段落；`CONTINUE_AFTER_COMMITTED` 表示从最后一个已发布段落的终点继续。补齐角色意愿、查世界书和修复保存格式，只能重写当前尚未提交的候选，不能重新执行本轮原方向、重复已发布的引荐、行程或问答。候选人物提示也使用相同范围，不再无条件要求从本轮开头写起。累计摘要保留前情，正文、结果、耗时与本段亲历只描述新增经过。

这项修改不扫描关键词裁剪正文，不替主 API 判定故事是否成立，不偷偷重写已经发布的故事或真实存档。针对性回归覆盖首段已发布、第二段角色调用暂停、正常恢复后只请求后续事件；真实主 API 的隔离重放保存原始回答供全文审读，不能把本地成功或调用完成直接等同于长期故事质量通过。

普通就近问询、查账、继续既定调查由主 API 自然衔接；需要新人物意愿时内部 `CONTINUE`。若已有实质结果、下一方向需玩家输入，则 `RESOLVED`，输入框提示大致行动。`OTHER` 不作为普通“去不去、继续还是休息”问句的兜底重要决策类型，仍由主 API 按实际关系、义务或风险判断真正的关键表态。

## 临写承接与实际参与者（连续游玩后续）

主 API 请求保留详细角色模板与世界书，在最后另附 `StoryAuthorContext` 直接投影：最后一段已发布故事、原玩家方向、每人的原身份、当前累计处境与最新本人意愿。这里没有另一次模型摘要，也不从正文推断位置、心情、同行结果或参与者。完整历史仍在前面的档案中；末尾投影帮助主创把近期事实和当前意愿与历史计划分清。粗粒度地点内的铺子、街头以已发布故事承接，不为每间铺面增加地理模拟。

本人历史中的 `ROLE_PROFILE` 明示为过去的主观想法，保留 `executionStatus`，不能冒充已经发生的 `TURN_EVENT`，也不能覆盖新一轮角色 API 的意愿。原 `SELF_PROFILE` 的结构化身份资料不再在裁剪旧动作字段时被清成空对象。这些变化只影响请求中的资料表达，不执行或删除旧计划，不改人物真实经历。

主创输出另列顶层 `roleIds`，包含本段实际有交流、对白或关键行动的既有人物；程序沿已有的结构化引用流程补齐本人意愿，不依赖此人恰好有移动、物品变化或 `roleExperiences` 才能发现。实际提供线索的新龙套用 `newCharacters` 简版留档，背景人群仍可概括。旧协议省略该名单不会新增阻断校验；已发布正文也不靠姓名关键词扫描或自动改写。

后续第17轮实际游玩发现，模型仍把“NPC取出自己的铜片、让玩家隔着查看”标成 `OTHER` 重要决策。新创作提示已不再提供 `OTHER` 兜底类别；`DECISION` 须写明 `stakes`，说明玩家此刻尚未授权的重大关系、义务、重要资源或危险变化。普通礼貌问句、NPC自己的动作和既定调查范围内的许可查看由主API自然写完。兼容读取旧 `OTHER` 存档，不在程序中按关键词改判、拦截或追加一个审核API。

角色API也有临写承接资料：完整本人历史以旧到新顺序展开，末尾直接附本人最近 `TURN_EVENT` 实际亲历、当前累计处境及本次要考虑的新交互。原查询仍取最近24条，原数据库记录不重排或改写；只是请求展示顺序改变，重用已排好的输入不会重复反转。过去准备查看的计划不能盖过较新“已经查看完成”的亲历。本次玩家提议是未来交互的创作方向，不等于人物已经获知玩家心思；角色只据自己的信息给出回应意愿和条件，主API仍负责全部对白、经过和结果。提出条件而对方尚未回应时，累计处境须保留“等待答复”，不能提前登记为已结盟或成交。
