# 重要剧情与伏笔：实现及针对性实测（2026-10-21）

## 本次实现

角色 API 继续只生成本人的档案、心理和意愿。主 API 先构思、再生成全部正文；既有定稿归档调用从同一篇正文整理实际结果。本次增加重要剧情的长期资料、伏笔关联与查阅，没有增加每轮独立的伏笔生成或评分调用。

### 存储与关联

- `story_plot_event`：重要剧情事件。以 `(session_id,event_id)` 为主键，保存类别、标题、当前进展、相关事实、阶段结果、原文来源及主创私有构思。
- `story_foreshadow`：重要伏笔。以 `(session_id,thread_id)` 为主键，通过 `(session_id,event_id)` 外键关联所属剧情，保存原始铺垫、具体问题、实际进展、回收解释与来源。
- 正式编号由服务分配，形如 `evt_…`、`fo_…`。同一次归档新建事件时，可用临时 `key` 引用，保存时绑定正式编号。后续沿用原编号。
- 每次保存同时在世界书留一份 `PLOT_EVENT` / `PLOT_THREAD` 历史快照，可按编号翻查旧版本和原章节。
- 新表加入现有完整检查点。回溯按父子顺序恢复，旧检查点没有新表字段时按空表恢复，不残留未来伏笔。
- 迁移 `migrate-story-plot-20261021.sql` 通过现有 `OperationSchema` 自动、幂等执行；不批量重写旧存档或为历史琐事补编号。

剧情是否重要、如何归类、伏笔是否已产生解释及后果，由主 API 根据正文整理。程序只处理存储、引用与查询，不根据关键词、地点、时间或轮数触发剧情，也不判定角色必须配合或玩家必须成功。

### 主创构思和查阅

`authorPlan` 支持结构化对象，旧字符串仍兼容：

```json
{
  "centralQuestion": "整段事件真正要处理的问题",
  "eventIds": ["evt_已有剧情编号"],
  "stakes": "人物各自的利害",
  "establishedCauses": ["带来源的既有起因和已兑现结果"],
  "possibleDevelopments": ["可修订的发展与阶段收束"],
  "keyScenes": ["少数值得展开的关键场景"],
  "unresolvedPlayerChoices": ["尚未授权的新重大选择"],
  "currentProgress": "已发表正文真正改变了什么"
}
```

构思跨补人物、换场、查档和操作恢复保留为 `episodePlan`。归档可用 `useAuthorPlan:true` 声明适用剧情，或者由主创自己的 `eventIds` 明确关联；实际保存的是主创原始构思，标记 `UNCOMMITTED_AUTHOR_PLAN`。归档回复自行编出的未来 `authorNotes` 不作为新剧情计划写入。

主创每次收到 `plotMemory`：至多 100 项精简事件索引和最近 4 项剧情的精简资料。近期展示最多 6 条起因事实、8 条伏笔及各伏笔最近 4 条进展，完整记录继续保留在库中。需要旧细节时使用：

```json
{"plotRequests":[{"eventId":"evt_…","limit":4,"includePassage":true}]}
```

也支持 `threadId`、`keyword`、`category`、历史 `beforeEntryId`、伏笔 `threadPage`。结果通过 `plotResults` 返回。查询不推进剧情、不重新请求角色意愿；按需继续主创时仍会发生正常的主创调用，因此不把主创查档后的续写宣传为“完全零费用”。

普通问路、买饭、每个新证人不各建一个剧情。一个重要事件跨章节继续更新原编号。伏笔的原问题得到解释并改变认识或处境后，应记录具体 `payoff`；所属事件尚未完全结束、玩家尚未决定后续善后，不应把已经回答的伏笔重新扩成更大的未知问题。

### 世界书界面与限知

世界书增加“重要剧情与伏笔”入口，可按关键词、剧情类别、剧情编号查询，展开关联线索，并免费读取本存档已发表的原章节。

- 限知只读取归档明确提供的 `playerView`；搜索范围、标题、状态、时间和线索数量均不使用隐藏资料。幕后更新没有新的玩家所知时，继续保留玩家此前所知及其时标。
- 天眼展示实际剧情事实和伏笔回收；未来作者构思不作为实际剧情展示。
- 切换视角、存档或分支立即清空旧结果，并拒绝较晚返回的旧请求。
- 普通世界书上下文、地点查询和继承世界的通用记录排除私有剧情快照，避免把主创未来构思当作已经发生的世界事实。主创查档走专用路径。

## 本地检查

最终相关回归覆盖：新事件及同批伏笔外键关联、重复提交、原始铺垫与历史查阅、跨存档引用隔离、隐藏状态搜索、自动上下文精简但完整资料可查询、分页、主创构思来源、定稿候选不冒充事实、第二轮接续、回溯及旧快照兼容。

前端覆盖剧情查询、原文查阅、自然语言状态、分页、视角切换、异步旧响应、存档分支切换和 HTML 转义。后端另覆盖大段剧情 JSON 在 MySQL 小排序缓冲区下的列表/查档，列表只排序编号等元数据，再读取正文，避免长期累积后查询失败。最终 **52 项后端相关测试、10 项前端测试通过**，后端打包与前端构建成功。默认回归不调用真实模型；只读付费归档探针需显式设置 `STORY_PLOT_LIVE_INPUT` 才会启用，且仅允许一次调用。具体证据见聊天工作区的实测报告和日志；这些本地测试不等于小说质量验收。

## 独立存档真实测试

本次只进行 **一次真实玩家行动**，没有连续跑故事：

- 独立存档 `plotprobe_f1ed14690`，人物沈砚与陆绫，调查旧账缺号与“双鹤”收条。
- 两段初始前文、人物已确立过往及最初的事件/伏笔记录是明确标注的测试夹具，不算新增生成成果。角色过往给出当事人真实经历，没有预设本次行动结果。
- 玩家请求并置旧账与收条，听当事人说明，然后再决定态度。
- 正文实际生成 1407 字符，操作 `COMPLETED`；角色、主创、归档各一次，共 3 次调用，估算 `¥0.048687`。
- 原剧情 `evt_probe_f1ed14690` 与原伏笔 `fo_probe_f1ed14690` 都沿用，没有另建一串事件；主创的结构化 `authorPlan` 实际引用了该事件编号。数据库最终仍是 1 项事件、1 项伏笔。
- 正文确实说明收条来历、另册登记及当事人的疏漏，没有继续转向下一个证人。已完整人工阅读正文，不能只凭 HTTP 成功或字数判定质量。
- 世界书限知查询、原章节接口和同操作重复提交实测无新收费；原长期存档完整内容摘要哈希前后相同。

### 实测发现及后续修正

1. **已解释的伏笔被善后选择拖成未解。** 首次归档将原问题追加“缺环如何了结”，仍写 `DEVELOPING`。已明确区分“这条线索是否得到解释”和“玩家是否接受后续安排”。对同篇原文做一次只读归档复测，原 `threadId` 返回 `PAID_OFF`、原问题保持明确，并给出实际解释与来源；没有生成新故事或改写原文。
2. **归档私自增加未来悬念。** 上述只读回复曾另提“分册焚毁可能另有隐情”。生产合并现在只绑定主创提供的原始构思，忽略归档自行新增的未来规划；相关本地测试覆盖这一来源区分。归档继续自由整理已发生结果，不替主创创作新剧情。
3. **第二轮补充记录读取类型错误。** 本地接续测试发现数组被旧对象读取方法解析，已修复；跨两轮与六章既有累计摘要回归通过。
4. **界面把中文进展状态显示为泛化标签。** 实测返回“已解释来路，缺环待了结”等自然语言状态，界面现保留原文字义。

归档复测只调用 1 次，估算 `¥0.013587`。本轮总计 **4 次实际调用、估算 `¥0.062274`**，输入 28850 tokens、输出 8356 tokens；用量均已确认，费用按项目配置估算，不是供应商结算账单。只读复测没有写回游戏结果，因此独立存档仍保留首次原始生成与归档，方便追查，不伪造修正后实录。

### 质量边界

原正文仍有“缺登记项”一度变成“少了一页”、追溯性补造已核对数字、普通文书善后被升级为重大选择，以及玩家保留态度前已代其说出部分采信等问题。主创提示已补上证据含义、已知与推断、玩家保留判断和新增实质风险的区分；本轮没有再次付费重抽正文，不能声称这些文学问题已获真实复测保证。

本次可以确认新增的编号、关联、归档、查阅和回溯链路已接入；伏笔回收含义已获得同篇正文的针对性真实复测。仍不能用这一场测试宣称所有长篇故事均可稳定达到小说水准。
