# 交付运行与维护

## 启动与停止

需要 Java 17+、Node.js、MySQL。默认数据库 bs，后端 8090，前端 5173。首次准备依赖、构建：

```powershell
cd backend
mvn '-Dmaven.repo.local=../.m2/repo' -DskipTests package
cd ../frontend
npm ci
npm run build
cd ..
```

配置见 `backend/src/main/resources/application.yml`。在启动终端设置 `MYSQL_BS_PASSWORD`、`LLM_MAIN_API_KEY`、`LLM_SUB_API_KEY`，按服务商设置模型名。不要把实际密钥写进文档。现有数据库不要运行 `init-all.sql`；它是空库初始化脚本。

本机实际模型密钥也可保存在 BS 目录下 `.runtime/bs-local-secrets.yml`，启动时自动导入；此文件不会进入后端 jar，也不应随源码或演示材料分发。2026-10-27已将现有源码中的模型密钥迁至该本地文件，保持原有主、副模型与备用密钥可用。`application.yml`及注释中只保留环境变量引用。登录签名仍由原签名文件管理，与模型密钥分开保存。

在 BS 目录运行：

```powershell
./scripts/start.ps1
# 可明确指定本机 Java/Node 路径：
./scripts/start.ps1 -JavaExe 'E:/javaee/jdk/jdk-21.0.7/bin/java.exe' -NodeExe 'D:/Node/node.exe'
./scripts/stop.ps1
```

启动脚本检查端口、进程和健康接口，将进程身份与日志写入 `.runtime/`；停止只处理该脚本记录且身份一致的进程。已有其他启动方式占用端口时会提示，避免误停服务。访问 `http://127.0.0.1:5173`。这是本机交付运行方式，公网部署需单独配置反向代理和 HTTPS。

健康检查、读档、世界书查询不调用模型。生成中断时先使用界面的续接，成功角色回复和已完成阶段会复用；不要为了网络错误重新创建人物或整个周目。

## 备份与恢复

先停止后端并保留原数据库。用 MySQL 自带 mysqldump 做完整备份，包括检查点、世界书、操作和费用账本：

```powershell
./scripts/backup.ps1 -Destination 'D:/游戏备份' -MySqlDumpExe '你的MySQL目录/bin/mysqldump.exe'
```

脚本从当前环境变量 `MYSQL_BS_PASSWORD` 取密码，通过子进程环境传递，不放到命令行参数；导出成功才写 manifest 与 SHA256，同时复制 `backend/.runtime/` 的登录签名。备份包含存档、私有角色资料及签名，应放在自己的备份目录。

恢复时先停止后端，在 MySQL 客户端确认目标库，再执行 `source 完整备份路径/database.sql`；将备份中的 `backend-runtime/` 恢复到 `backend/.runtime/` 后启动。先在独立空库演练恢复，确认备份可读，再替换正式数据。

## 旧存档时间修复

正常游玩的时间来源统一为主创定稿：主创 `timeProgress.elapsedParts` 的原单位数量优先于旧 `elapsedSeconds`；旧秒数格式仍兼容。服务器只做单位换算，归档不再另算一个时钟覆盖它。只有主创完全没给耗时的旧格式，归档才补估计。归档原来给出的不同值保存在私有 `archiveTimeInterpretation` 和原始回复中。正常归档、合并、缓存恢复与非归档故事模式使用同一来源。

可先免费审计全部已完成操作中有明确原单位的记录：

```powershell
python scripts/audit_story_time.py --out time-audit.json
# 或只审计一个存档：
python scripts/audit_story_time.py --session 存档编号 --out time-audit.json
```

审计仅比较明确的结构化数量，不解读故事日期或调用模型；多片段回合不会把最后片段跨度错当整个回合。没有原单位的旧记录会单独计数，不冒称已核实其文学时间线。

`scripts/story_time_repair.py` 只修正已有数值时钟，不读取故事关键词，也不决定剧情能否发生。需要 Python + PyMySQL。依据原归档明确写出的数量提供修正；含糊的月份、互相矛盾的正文不能凭程序猜测。

修正文件示例（logId、原起讫秒数必须来自待修存档）：

```json
{"sessionId":"目标存档编号","corrections":{"123":{"expectedStart":900,"expectedEnd":6300,"elapsedParts":[{"amount":1.5,"unit":"SHICHEN"}],"basis":"原主API归档明确一个半时辰，却误记为5400秒"}}}
```

后端停止时运行，先生成可审阅计划：

```powershell
python scripts/story_time_repair.py plan corrections.json my-save.repair-plan.json
python scripts/story_time_repair.py apply my-save.repair-plan.json
# 尚未继续游玩、存档未改变时可精确撤回：
python scripts/story_time_repair.py rollback my-save.repair-plan.json
```

计划包含修正前后完整相关行、证据、摘要哈希与变更清单。应用在单一事务中完成，存档已改变或校对不通过时不提交。同步章节、世界书时刻、剧情与伏笔来源、角色已存时刻、运行时钟、检查点及各自历史分支；其他分支用自己的章节编号识别，不能按相同秒数误改。保留原故事、玩家原话、原始模型响应、世界刻数和费用。区间内部已存数值时刻按原区间比例映射，区间后的时刻累计平移；这是旧时钟坐标修正，不重写故事先后。

该工具不是完整数据库备份的替代。计划含私有存档，保存在备份目录，勿提交仓库。正常游戏继续使用主API给出的原单位与 `StoryDuration` 换算；无需每轮运行此工具。

## 免费组合检查与真实验收

```powershell
cd backend
mvn -o '-Dmaven.repo.local=.m2/repo' -Pintegration '-Djacoco.append=false' verify
cd ../frontend
npm test
node --test tests/*.test.mjs
npm run build
cd ../scripts
python -m unittest -v test_story_time_repair test_audit_story_time
```

后端组合测试使用模拟模型和实际测试数据库，不产生模型费。真实验收需另留少量预算，人工连续阅读：重要选择是否保留边界、已完成事件是否重演、时间起讫能否连起来、人物改变是否有来由、结束阶段目标后活着是否仍可继续、死亡/主动终老是否才触发终局。接口成功不能代替小说质量验收。
